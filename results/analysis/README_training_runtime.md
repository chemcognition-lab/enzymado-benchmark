# Training runtime breakdown

`training_runtime_breakdown.csv` is a long-format table, one row per
**(SLURM job, array index, task)** block found in the `enzymado_train_*.out` /
`enzymado_attn_*.out` logs in the repo root, cross-referenced with `sacct`
job state. It's meant as raw material for someone (or an agent) to look for
runtime-optimization opportunities across the training pipeline.

Generated by a one-off parser (not checked into the repo) that scans log
timestamps between consecutive `Task: <name> | type: ... | split: ...`
markers to get a duration, and pulls `sacct` for the ground-truth job outcome.

## Columns

| column | meaning |
|---|---|
| `job_id`, `array_idx` | SLURM array job id / task index |
| `launcher` | `no_attention` (`run_training_cluster.slurm`) or `attention` (`run_training_attention_cluster.slurm`) |
| `slurm_state` | final SLURM state for that array task: `COMPLETED`, `TIMEOUT`, `OUT_OF_MEMORY`, `RUNNING`, `CANCELLED` |
| `slurm_req_mem` | `--mem` requested for that job |
| `slurm_job_total_elapsed_s` | total wall time for the whole array task (spans *all* tasks it processed, not just this row) |
| `embedding` | embedding model name |
| `embedding_dim` | embedding vector dimensionality (from `embeddings_models_output.json`) |
| `task_name`, `task_type`, `split` | benchmark task, regression/classification, random/similarity(loco) |
| `model_prefix_filter` | `MODEL_PREFIX` env var used for that submission, if any |
| `families_trained_this_block` | which model families (`linear`/`mlp`/`xgboost`) were actually fit fresh in this block (empty if all were skipped as already-done, or if the task itself was skipped) |
| `models_skipped_already_done` | families that were already complete and skipped |
| `n_train_rows` | training rows loaded for this task (proteins, or protein-residue rows before concatenation) |
| `n_train_residues_concat` | for residue tasks: total concatenated residue count actually fed to the model |
| `route` | training route (`global` for pooled/vector tasks, `residue` for per-residue tasks) |
| `duration_seconds` | wall time of *this task block* (from its `Task:` line to the next one / `Done.`) — includes data loading, embedding-store materialization, training, and prediction/saving for whichever families ran |
| `error` | error message if the task block ended in an exception (truncated to 200 chars) |

## Important caveats before drawing conclusions

- **`duration_seconds` is per task block, not per model family**, when
  `model_prefix_filter` is empty (the default): a block may train 1-3
  families (linear/mlp/xgboost) sequentially, so the timing conflates them.
  For clean single-family attribution, filter to rows where
  `families_trained_this_block` contains exactly one value (also true
  whenever `model_prefix_filter` was set, e.g. the `xgb_`/`mlp_` resubmits).
- **Failed/killed runs still have a duration** — it's the time elapsed until
  the crash/OOM/timeout, not a full training time. Check `slurm_state` and
  `error` before treating a duration as "how long a successful run takes".
- **`slurm_job_total_elapsed_s`** is the same value repeated across every
  row from the same array task (since sacct only reports it at that
  granularity) — don't sum it across task rows from the same job/array_idx,
  only across distinct `(job_id, array_idx)` pairs.
- Residue-embedding-store materialization time (loading embeddings into RAM
  vs lazy streaming, logged separately in the raw `.out` files as
  `Residue store auto-selection: ... -> materialized|lazy`) is *included* in
  `duration_seconds` but not broken out as its own column — for the biggest
  embeddings this can be 2-3 minutes of the block by itself, independent of
  actual model fitting time.

## Headline numbers as of this generation

Across 269 distinct (job, array-task) submissions tracked in `sacct` since
2026-01-01 for this pipeline:

- **~845 GPU-hours** spent in total.
- Of that, **~349h (41%) ended in TIMEOUT**, **~82h (10%) in OUT_OF_MEMORY**,
  and only **~309h (37%) COMPLETED** cleanly (~106h still RUNNING at
  generation time). This is the single biggest optimization target: most
  spent compute never finished, likely due to under-provisioned
  `--time`/`--mem` for the larger embeddings (`ankh3_xl`, `esm2_3B`,
  `ankh3_large`, `ankh_large`, `esm2_650M`) combined with the heavier
  `attention` launcher (815.8h of the 845h total came from `attention` jobs
  vs 29.2h from `no_attention`).
- Checkpointing means a TIMEOUT is not fully wasted work (it resumes), but
  each restart still re-pays data loading + embedding-store materialization
  time before continuing.
